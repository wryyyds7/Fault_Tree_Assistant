## 一、高风险缺陷（必须立刻修复）

### 1.1 document-ingest-service：PDF/DOCX 解析是占位代码

**问题描述**：
- `parsePdf()` + `parseDocx()` 仅返回 `"PDF document content: x"` 等占位文字
- 未实现真实内容解析（无 Apache PDFBox / POI 调用）
- 无 OCR 功能（仅有 TODO 注释）
- `countPdfPages()` / `countDocxPages()` 固定返回 1
- `processDocument()` 直接用文本行做段落，不做语义/章节解析
- `extractStructuredContent` 仅 `split("\n")`，未进行句法/实体抽取、事实三元组
- `queue.document.parse` 仅发消息，未实现状态回写（文档状态一直停留在 "queued/processed"）

**影响**：
- AI 生成故障树时无真实文档内容输入
- 整个"知识抽取"链路断裂
- 不符合项目要求的"知识抽取"核心功能

**修复行动**：

| 序号 | 修复内容 | 目标文件 | 工作量 |
|------|---------|---------|-------|
| 1.1.1 | 实现 PDF 真实解析（使用 Apache PDFBox） | `DocumentParser.java` | 2-3 天 |
| 1.1.2 | 实现 DOCX 真实解析（使用 Apache POI） | `DocumentParser.java` | 2-3 天 |
| 1.1.3 | 实现段落语义解析（句法分析、实体识别） | `ParagraphExtractor.java` | 3-4 天 |
| 1.1.4 | 实现结构化内容抽取（章节、标题层级） | `StructuredContentExtractor.java` | 2-3 天 |
| 1.1.5 | 实现文档解析状态回写（doc-status -> completed） | `DocumentStatusManager.java` | 1-2 天 |
| 1.1.6 | [可选] 实现 OCR 功能（PDF 扫描件） | `OcrProcessor.java` | 3-4 天 |

**验收标准**：
- 上传真实 PDF/DOCX 文件后，能提取出完整的文本段落
- 段落包含：页码、章节标题、内容文本
- 文档状态能正确更新为 "completed"

**参考实现**：
```java
// PDF 解析示例（Apache PDFBox）
try (PDDocument document = PDDocument.load(pdfFile)) {
    for (int pageNum = 0; pageNum < document.getNumberOfPages(); pageNum++) {
        PDPage page = document.getPage(pageNum);
        PDFTextStripper stripper = new PDFTextStripper();
        stripper.setStartPage(pageNum + 1);
        stripper.setEndPage(pageNum + 1);
        String text = stripper.getText(document);
        // 进一步解析段落、章节
    }
}
```

### 1.2 rag-generation-service：_get_document_content 是模拟数据

**问题描述**：
- `_get_document_content()` 是模拟静态语句，没有调用 `document-ingest-service` REST API
- 未使用真实检索文本
- `LLMClient.generate()` 失败时返回硬编码默认 JSON（风险高）
- `FaultTreeGenerator._extract_json()` 仅用正则 `\{.*\}`，非健壮，容易把异常文本解析成错误树

**影响**：
- RAG 生成不依赖真实文档内容
- AI 生成结果与文档无关
- 无法实现"文档溯源"和"证据链补全"

**修复行动**：

|------|---------|---------|-------|
| 1.2.1 | 实现真实调用 document-ingest-service 获取文档内容 | `rag_api.py` | 1-2 天 |
| 1.2.2 | 实现调用 vector-store-service 获取向量检索结果 | `rag_api.py` | 1-2 天 |
| 1.2.3 | 重构 LLMClient.generate() 错误处理（不返回硬编码） | `llm_client.py` | 1 天 |
| 1.2.4 | 增强 _extract_json() 健壮性（JSON5 / 异常恢复） | `fault_tree_generator.py` | 2 天 |
| 1.2.5 | 实现调用 rule-validation-service 进行结果稽核 | `rag_api.py` | 1-2 天 |
| 1.2.6 | 实现回填 source_evidence（溯源证据） | `rag_api.py` | 1-2 天 |
| 1.2.7 | 实现输出结构准确率 | `evaluation_metrics.py` | 1-2 天 |

**验收标准**：
- RAG 生成时能从后端服务获取真实文档段落
- AI 生成结果包含 source_evidence 字段
- 结构准确率可计算并返回

### 1.3 vector-store-service：向量检索未真正实现

**问题描述**：
- `getVectorsByDocId` 仅返回元数据，不是真正的向量
- `searchSimilarVectors` 未见向量搜索核心实现
- 向量没有持久化，不跨重启
- 没有从 vector-store-service 读写数据

**影响**：
- RAG 检索依赖向量相似度，当前无法实现
- 文档内容无法向量化存储

### 2.2 knowledge-graph-service：KG 逻辑过浅

**问题描述**：
- `queryTemplate()` 逻辑过于简单：找不到时仅构造空 OR 模板，不真正匹配/推荐库中模式
- `enrichKnowledge()` 仅处理单条 (cause, effect)，未支持复杂因果图/权重
- `initializeOntology()` 仅建基本节点，未加载真实 ISO 13379 本体文件、未检查同义词、未同步文档来源
- `createOrUpdateEvent()` 总是新建，未检查已有节点合并

**影响**：
- 知识图谱不完整，无法提供深度语义支持
- 不符合"知识图谱可扩展"与"标准模板优先"要求

## 七、结论

**核心问题**：当前代码"骨架齐全"但"核心 AI 业务链条很多地方还是轻量/占位、不符合项目要求"。

**必须立即修复**：
1. 文档解析（PDF/DOCX）占位代码 → 真实解析

**要达到竞赛要求**，需要补足：
- 📌 **知识抽取**（Document → Vector → KG）
- 📌 **生成逻辑可验证**（RAG → Rule Validation → Source Evidence）
- 📌 **反馈闭环**（Expert Feedback → KG/RAG Update）

**预计工作量**：
- 高风险修复：15-20 天
- 中风险修复：20-25 天
- 低风险修复：15-20 天
- **总计：50-65 天**
